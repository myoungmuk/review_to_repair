## 프롬프트 (복붙용)

```text
첨부한 최종 논문 PDF(KCC_2026)를 기반으로 KCC 2026 논문대회 발표용 PPT를 만들어줘.

[중요 — 발표 형식]
이 PPT는 단순 요약본이 아니라, 발표자가 실제 논문을 보면서 설명하는 학회 발표 자료다.
논문 PDF의 실제 페이지 일부를 캡처 이미지처럼 보여주고, 그 위에 박스·화살표·번호 태그를
넣어 "이 부분이 연구 질문", "이 부분이 실험 설계", "이 부분이 핵심 결과", "이 부분이 한계·
후속연구"임을 짚어주는 구성을 포함해줘.

[발표 목적]
- KCC 2026 논문대회 발표
- 발표 시간: 10~15분 (슬라이드 20장, 장당 약 40초 기준)
- 청중은 Review-to-Repair와 코드 LLM을 어느 정도 알지만, 본 논문의 실험 구조는 처음 본다고 가정
- 발표자가 슬라이드를 보며 자연스럽게 설명
- 글은 적게, 핵심 메시지와 시각자료 중심
- 발표의 숨은 목표: "왜 이 주제를 골랐고, 왜 이렇게 설계했고, 왜 이 데이터·모델을 썼는지"
  그 과정과 의사결정이 청중에게 전달되도록 구성할 것

[논문 정보]
- 제목: Review-to-Repair에서 정답 위치·Diff 유형 정보의 효과 진단
- 영문: Diagnosing the Effects of Gold Location and Diff-Type Information in Review-to-Repair
- 저자: 강명묵(제1저자), 양근석(교신저자)
- 소속: 한경국립대학교 컴퓨터공학전공
- 지원: 한경국립대학교 국립대학육성사업(2026)

[발표 전체 핵심 메시지]
리뷰 기반 코드 수정에서 모델의 실패 원인을 단순히 "수정 위치를 못 찾기 때문"으로 설명할
수 있는지 진단한다. 실험 결과, 리뷰 코멘트 제공은 정확 일치율과 변경 라인 중첩 F1을 모두
향상시켰다. 그러나 정답 위치·diff 유형 정보를 제공한 gold_location 조건은 변경 라인 중첩
F1은 높였지만 정확 일치율은 오히려 감소시켰다. 즉, 모델이 어디를 수정해야 하는지 더 잘
맞춰도, 실제 정답 코드를 정확히 생성하는 것은 별개의 문제일 수 있다.
캐치프레이즈: "위치를 아는 것과 정확히 고치는 것은 다르다."

[반드시 반영할 핵심 실험 정보]
- 데이터셋: CodeReview-New 전체 14,855개 예제 (코드 스니펫/hunk 단위)
  · 선정 이유: 리뷰 코멘트·수정 전 코드·정답 코드 삼중쌍이 갖춰진 대규모 공개 벤치마크라
    조건 통제 진단에 적합
- 모델 3종 (로컬 코드 LLM, 무료·결정론적 실행):
  1. qwen2.5-coder:7b
  2. deepseek-coder:6.7b
  3. qwen2.5-coder:32b (대형 대조군)
  · 선정 이유: 7B급 2종으로 모델 다양성 확보 + 32B 대형 모델을 더해 "모델을 키우면
    위치 정보가 정확 수정으로 전환되는가"까지 점검
- 입력 조건 3가지:
  1. no_review: 수정 전 코드만 제공
  2. direct: 수정 전 코드 + 리뷰 코멘트
  3. gold_location: 수정 전 코드 + 리뷰 코멘트 + 정답 위치·diff 유형 마커
- 통제: 동일 예제·동일 프롬프트 형식·동일 후처리, temperature=0.0(결정론적), num_predict=512
- 총 출력 수: 133,695개 (14,855 × 3조건 × 3모델), 무결성 검증 결과 누락·중복·생성/추출/평가
  오류 모두 0
- 평가 지표 2종:
  1. exact_match_line_trim: 출력과 정답이 줄 단위 우측 공백 제거 후 완전 일치하는지 (보수적
     0/1 표면 일치 지표, 실행 기반 정확성 아님)
  2. location_overlap_f1: 모델이 바꾼 라인과 정답 변경 라인의 중첩(스니펫 내부 changed-line
     overlap, full-file localisation 아님)
- 조건 간 차이는 paired bootstrap(1,000 iterations, seed=42)으로 95% 신뢰구간 제시

[핵심 수치 — 모두 3모델 macro 평균 기준]
RQ1. 리뷰 코멘트 제공 효과 (direct - no_review)
- 정확 일치율: 0.0049 → 0.0729 (Δ +0.0680, 95% CI [0.0657, 0.0705], 0 미포함)
- 변경 라인 중첩 F1: 0.3744 → 0.5306 (Δ +0.1562)

RQ2. 정답 위치·diff 유형 정보 효과 (gold_location - direct)
- 변경 라인 중첩 F1: 0.5306 → 0.6167 (Δ +0.0861, 95% CI [0.0830, 0.0892])
- 정확 일치율: 0.0729 → 0.0382 (Δ 약 -0.0346, 95% CI [-0.0371, -0.0322], 오히려 감소)

RQ3. 위치 중첩 개선이 정확 일치율 향상으로 전환되는가 (모델별)
- qwen2.5-coder:7b: Loc.F1 +0.1660, Exact -0.0240
- deepseek-coder:6.7b: Loc.F1 +0.0447, Exact -0.0009 (거의 변화 없음)
- qwen2.5-coder:32b: Loc.F1 +0.0477, Exact -0.0790
- 핵심: 모델이 클수록 Exact 낙폭이 더 크다 (7b -0.024 ≪ 32b -0.079).
  direct 정확 일치율이 가장 높았던 32B(0.1208)가 gold_location에서 가장 큰 감소를 보였고,
  gold_location 변경 라인 중첩 F1은 0.7007로 가장 높았음.

[왜 떨어지는가 — 결정적 증거 (논문 5.1절)]
- qwen2.5-coder:32b에서 direct 성공→gold_location 실패로 뒤집힌 사례 1,425개,
  반대(실패→성공) 251개 → 순감소 1,174개
- 감소 사례의 62.9%(896개)는 gold_location의 변경 라인 중첩 F1이 1.0 (위치는 완벽히
  맞췄는데 정답 코드 생성 실패) ← "위치를 알아도 못 고친다"의 직접 증거
- 528개는 정답 라인보다 더 넓게 수정한 과편집(over-edit) 의심
- diff 유형 비대칭: delete_only에서는 gold_location이 정확 일치율을 높였으나,
  replace_only에서는 변경 라인 중첩 F1이 올라도 정확 일치율은 떨어짐(과편집 유발)
- 이 감소는 의심 출력(suspicious output, 마커 echo 등) 제거 후에도 유지됨 → 단순 출력
  형식 오류가 아니라 실제 모델 행동

[PPT 전체 구성 — 총 20장]

1. 표지
- 제목: Review-to-Repair에서 정답 위치·Diff 유형 정보의 효과 진단
- 부제: 정답 위치를 알려주면 모델은 실제로 코드를 더 잘 고치는가?
- 저자: 강명묵, 양근석(교신저자)
- 소속: 한경국립대학교 컴퓨터공학전공 / KCC 2026 논문대회 발표
- 디자인: 흰색 배경, 파란색 포인트, 코드 블록 또는 LLM 아이콘

2. 발표 흐름 (목차)
- 연구 배경 → 문제의식 → 관련 연구·차별점 → 연구 질문 → 실험 설계 →
  평가 지표 → 실험 결과(RQ1/RQ2/RQ3) → 왜 떨어지는가 → 평가 범위·한계 →
  후속 연구 → 결론

3. 실제 논문 한눈에 보기
- 논문 PDF 1~3페이지를 작은 썸네일로 나란히 배치
- 1페이지: 연구 배경·문제의식·기여 / 2페이지: 실험 설계·조건·지표·그림 / 3페이지: RQ 결과·토의·한계·결론
- 말풍선: "오늘 발표는 이 논문의 실험 설계와 결과 해석을 중심으로 설명하겠습니다."

4. 연구 배경: Review-to-Repair란?
- 코드 리뷰 코멘트를 바탕으로 수정 전 코드를 고치는 작업
- 흐름도: old code + review comment → Code LLM → revised code
- 발표자 노트: "일반적인 코드 생성이 아니라, 리뷰 코멘트를 보고 기존 코드를 어떻게 고칠지
  생성하는 문제입니다."

5. 문제의식: 실패 원인을 분리해서 봐야 한다
- 코드 LLM이 수정에 실패했을 때 가능한 원인 3가지
  1. 리뷰 의미 이해 실패  2. 수정 위치 파악 실패  3. 코드 편집 생성 실패
- 핵심 질문: "정확 일치율이 낮은 이유가 정말 위치를 못 찾아서일까?"
- 시각자료: 세 갈래 원인 다이어그램
- 발표자 노트: "기존 연구는 실패했다는 결과는 알지만, 왜 실패했는지는 분리하지 않았습니다."

6. 관련 연구와 본 연구의 차별점
- 기존 흐름: Tufano(ICSE'21/'22) 리뷰 기반 코드변경 자동화, Li 등 CodeReviewer(FSE'22)
  대규모 사전학습, Huq 등 Review4Repair(IST'22) 리뷰를 APR에 통합
- 공통 한계: 대부분 end-to-end 성능 지표만 평가 → 실패가 리뷰 이해·위치 파악·편집 생성
  중 어디서 났는지 분리하지 않음
- 본 연구의 차별점: 새로운 수정 시스템 제안이 아니라, 입력 조건을 통제해 실패 원인을
  단계별로 분리하는 "진단(diagnostic)" 연구
- 발표자 노트: "본 논문의 핵심은 더 좋은 모델을 만드는 게 아니라, 실패의 원인을
  쪼개서 보는 진단 프레임을 제안하는 것입니다."

7. 논문 페이지 기반 설명: 연구 질문 위치 강조
- 논문 1페이지 서론 영역을 크게 배치, 연구 질문 문장에 파란 박스
  "정답 변경 위치 정보를, 나아가 diff 유형까지 함께 제공하면 모델은 실제로 정답 코드를
   더 잘 생성하는가?"
- 오른쪽 해석:
  · 위치를 알려줬을 때 성능↑ → 위치 탐색이 병목
  · 위치를 알려줘도 성능 정체/하락 → 편집 생성이 병목일 가능성

8. 연구 기여
- 카드형 3개: (1) 리뷰 효과와 위치·diff 효과를 분리하는 3조건 진단 프로토콜
  (2) CodeReview-New 14,855개 × 3 로컬 LLM 대규모·일관성 검증
  (3) 위치 중첩 향상이 정확 일치율 향상으로 전환되지 않음을 실험적으로 제시
- 발표자 노트: "숏 논문이라 기여는 간결하게, 실험 질문과 결과 중심으로 구성했습니다."

9. 실험 조건 설계
- 표로 세 조건 비교 (no_review / direct / gold_location)
- 비교 의미: direct - no_review = 리뷰 코멘트 효과 / gold_location - direct = 위치·diff 정보 효과
- 발표자 노트: "모델과 데이터는 고정하고 입력 조건만 바꿔, 어떤 정보가 성능에 영향을
  주는지 분리했습니다."

10. gold_location은 무엇인가?
- 정답 diff에서 얻은 위치와 replace/delete/insert 유형만 알려주는 oracle 진단 조건
- 중요한 제한: 정답 new 코드의 토큰·실제 수정 내용은 제공하지 않음
- 예시 마커:
  <GOLD_LOCATION_START id="1" tag="replace">
  old line
  </GOLD_LOCATION_END id="1">
  <GOLD_INSERTION_POINT id="2" />
- 강조: "정답 위치는 알려주지만, 정답 코드는 알려주지 않는다."
- 발표자 노트: "이건 배포용 조건이 아니라, 위치를 알았을 때도 실패가 남는지를 보는
  진단용 oracle 조건입니다."

11. 왜 이 데이터·모델을 골랐나
- 데이터: CodeReview-New — (old, review, new) 삼중쌍이 갖춰진 대규모 공개 벤치마크.
  정답 diff에서 위치·유형 마커를 자동 생성할 수 있어 조건 통제 진단에 적합
- 모델: 7B급 2종(qwen2.5-coder:7b, deepseek-coder:6.7b)으로 모델 다양성 +
  대형 32B(qwen2.5-coder:32b)로 "모델 규모를 키우면 결과가 달라지는가" 확인
- 실행: 전부 로컬 코드 LLM, temperature=0.0으로 재현 가능하게 통제
- 발표자 노트: "특정 모델 한 개의 우연이 아님을 보이려고 규모가 다른 세 모델을 함께
  비교했습니다."

12. 전체 실험 프로토콜 (그림 1 재구성)

13. 평가 지표 설명
- exact_match_line_trim: 줄 단위 우측 공백 제거 후 완전 일치하면 성공

14. 실험 결과 1 — RQ1: 리뷰 코멘트 제공 효과
- 질문: direct는 no_review보다 정확 일치율을 높이는가? (3모델 평균)
- 정확 일치율 0.0049 → 0.0729 (Δ +0.0680) / 변경 라인 중첩 F1 0.3744 → 0.5306 (Δ +0.1562)

- 발표자 노트: "더 큰 모델을 더해도, 오히려 잘하던 모델일수록 위치 정보 때문에 정확

17. 왜 떨어지는가 — 핵심 진단 (논문 5.1절)
- 32B에서 direct 성공→gold 실패 1,425건 vs 반대 251건 (순감소 1,174건)
- 감소 사례의 62.9%는 위치 완벽(Loc.F1=1.0)인데 실패 ← "위치를 알아도 못 고친다"
- diff 유형 비대칭: delete_only는 gold가 도움 / replace_only는 과편집 유발(주범)
- 의심 출력 제거 후에도 감소 유지 → 단순 출력 형식 문제 아닌 실제 행동
- 발표자 노트: "위치를 완벽히 맞췄는데도 정답 코드를 못 만든 경우가 감소분의 60% 이상입니다.
  이게 '위치는 충분조건이 아니다'의 가장 직접적인 증거입니다."
```
